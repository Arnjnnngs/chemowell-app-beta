# Keeping one patient's app out of the product — the research, and four options

**Aaron, 2026-09-13:** *"I don't like it that it can still happen. There need to be 2-3 Claude.md,
1 for each. I don't care if all the code need rewritten for chemowell. This is not acceptable and
can't be allowed. Even if I have to create another chat and keep things separate and have you call
another chat for caretracker. Figure it out and give concrete options."*

---

## What the research found

### 1. The root cause is a filename, and Aaron guessed it exactly right

| repo | its instruction file | auto-loaded by Claude Code? |
|---|---|---|
| `care-tracker` | `CLAUDE.md` — **719 lines** | **YES** |
| `chemowell-app-beta` | `APP_CLAUDE.md` — 108 lines | **NO** |
| `chemowell-beta` | `BETA_CLAUDE.md` — 102 lines | **NO** |

Claude Code auto-loads a file named exactly `CLAUDE.md`. The two ChemoWell repos had real rules —
including repo boundaries and a Firestore-collection separation rule — sitting in files the loader
has never once read. **The only standing brief in any session touching any of these three repos was
the one for the other patient's app:** 719 lines naming her nine times and listing four of her
medications.

So every session was briefed on her, never briefed on this product, and then wrote this product's
code. That is the mechanism, and it is not a wording problem.

**FIXED, in this change.** Both files renamed to `CLAUDE.md`, with a new **Rule 0 — who this app is
for** at the top of each, naming the four shapes the leak takes. References updated in
`release_check.sh` and the READMEs.

### 2. ChemoWell's own rules never stated the rule

`APP_CLAUDE.md` mentioned care-tracker four times and contained **zero** occurrences of "product",
"stranger", "not one person", or anything equivalent. Even if it had loaded, it did not say the
thing. **FIXED** — Rule 0 says it first, in plain words, with the history attached.

### 3. Hooks work here, contrary to what the notes say

`care-tracker/CLAUDE.md` records that a Stop hook "cannot be installed from a cloud session". That is
no longer true: `~/.claude/launcher-settings.json` currently registers a live `SessionStart` hook and
a live `Stop` hook, both running every turn. **Mechanical enforcement at session boundaries is
available.** Note the caveat: that file is regenerated by the environment, so a durable hook belongs
in a repo's own `.claude/settings.json`, which is committed and survives.

### 4. All three repos share one working directory

Every session starts at `/home/user` with all three repos beside each other. Nothing scopes a session
to one product; the separation has only ever been my attention.

## The four options

### Option A — Per-repo `CLAUDE.md` (**DONE in this change, no decision needed**)

Each repo now carries its own `CLAUDE.md` and each opens with Rule 0. Cost: an hour, already spent.

**What it fixes:** ChemoWell's rules are now loaded instead of invisible, and the product-identity
rule is stated where a session will actually meet it.
**What it does NOT fix:** a session working in ChemoWell can still load care-tracker's `CLAUDE.md`
too, because both repos sit under one working directory and reading any file in the other pulls its
instructions in. **A is necessary and not sufficient.** That is the honest limit, and it is the
reason options B and D exist.

### Option B — One session per product (**Aaron's own suggestion; RECOMMENDED**)

Start a session bound to **one** repo. Care-tracker work is handed to a **separate session** created
for it. I can create and drive that second session myself — the tooling for it is already in this
environment — so this does not become a chore for Aaron: he stays in one chat, and I open a second
one for the other product when it is needed and report back.

- **Fixes:** the instruction leak completely. A ChemoWell session never loads her app's brief, never
  reads her medication list, never sees her care plan. There is nothing to leak.
- **Costs:** cross-repo ports (v72 and v73 were shipped to all three) need a deliberate handoff
  instead of happening inside one head. That is a real cost and it is also a benefit — a port becomes
  an explicit, reviewable act rather than a copy-paste.
- **Effort:** small. Mostly a change in how a session is started.

### Option C — A hook that refuses (**cheap, RECOMMENDED alongside B**)

A `SessionStart` hook in each repo's `.claude/settings.json` that states which product this session
is for and refuses to proceed silently if another product's repo is also present in the working
directory. Plus wiring `test/v75-no-other-patient.mjs` into `release_check.sh` so the four-shape check
runs on every release rather than when someone remembers.

- **Fixes:** makes A and B enforced instead of remembered. Hooks are proven to work here.
- **Costs:** an hour or two. Small risk of being noisy; a hook that cries wolf gets disabled.
- **Effort:** small.

### Option D — Sever the code ancestry (**the real fix for the code, Aaron has pre-approved the scope**)

Aaron: *"I don't care if all the code need rewritten for chemowell."* That is `HARDCODED_MEDS_PLAN.md`
phases 1–3, written 2026-08-19 and never started:

1. **Phase 1** — make the eight hardcoded behaviours expressible as medication properties
   (`chemoBlock`, `chemoRelativeWindows`, `linkedTo`, `interactions`, `homeCard`, `ceilingGroup`).
   Each code path reads the property and falls back to the old branch. **Nothing changes for anyone**;
   every suite staying green is the proof.
2. **Phase 2** — express each of the thirteen legacy ids as properties, delete the hardcoded branch,
   and prove equivalence by simulating a full chemo cycle old-path vs new-path with **zero**
   differences. This deletes `zofranBlockedOn`, `dexWindowsForOffset`, `protonixMorningLogTs`,
   `protonixEveningLogTs`, `tylenolMg`.
3. **Phase 3** — delete `RESERVED_LEGACY_MED_IDS`. A user can then name their medication Zofran, get
   the id `zofran`, and get **only** the behaviour they configured.

- **Fixes:** the thing the leak attaches to. Also returns thirteen real drug names to customers who
  currently cannot use them.
- **Costs:** this is the scheduling engine of a medication app. A mistake does not crash; it shows up
  as a dose that was never prompted for. Needs equivalence testing, its own release per phase, and
  an audit each time. **Size: L.** Phase 4 (editor UI so a user can actually set these) is a further
  release with a design pass.
- **Effort:** the largest item here by a wide margin, and the only one that removes the problem
  rather than containing it.

---

## Recommendation

**B + C now, D next, A already done.**

A alone would leave the same hole in a different shape. B is the only option that makes the
instruction leak structurally impossible rather than guarded against, and it is what Aaron proposed.
C makes B stick without relying on anyone remembering. D is the one that matters most in the long run
and is the one he has already pre-approved the scope for — but it is an L and it should not be
started in the same breath as shipping app-v75.

**Sequence:** finish app-v75 (it is green and waiting on a ship decision) → B and C, which are hours
→ D phase by phase, each with equivalence proofs and its own audit.

## What this does not fix, stated plainly

- **Features shaped by one clinical case.** The paracentesis screen exists because of one patient's
  ascites. It is a legitimate feature for some users and dead weight for most. Not addressed by any
  option above; worth a separate conversation about what ChemoWell is for.
- **`tools/med-list.json`.** The 113 drugs fetched from MedlinePlus were chosen against one
  regimen plus common chemotherapy agents. It should be derived from something neutral.
- **The shared Firestore project.** Both apps use `fuelforge-7c132`. The collections are separated
  and a hard rule forbids crossing them, but they are one project-level setting apart.
